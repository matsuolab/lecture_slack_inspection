# 違反検知の判定方式の見直し（gpt-4o-mini 廃止への対応）

- 作成日: 2026-10-13
- 対象: `lambda/app_inspect`（違反検知）。`app_batch` も同じ判定を使う
- ステータス: 検証完了・実装済み（未コミット・未デプロイ）

## 1. 結論

- 本番の判定モデル gpt-4o-mini は廃止予定。**プロンプトを変えずにモデルだけ gpt-6-luna に替えると、判定漏れが約 6 倍に増える**（開発用データで取りこぼし 10 → 58 件）。モデルの差し替えだけでの移行は危険。
- 判定の問い方・方針・判定の仕組みを作り直した新方式は、gpt-4o-mini を使わずに、**判定漏れを今の本番より減らし（取りこぼし 11 → 1 件）、誤検知を約 80% 減らした**（665 → 134 件。評価用データ 925 件）。
- 新方式の主経路は **OpenAI Decisions API（gpt-6-luna）**。費用は今の本番の約 75%、警告しない投稿の判定時間は約 4 分の 1（1.1 → 0.3 秒）。
- Decisions API は Public Beta のため、**gpt-6-luna の Chat Completions だけで動く予備経路**も用意した。予備経路だけでも今の本番を上回る（取りこぼし 3 件・誤検知 132 件）。
- 警告した投稿には必ず条文が付く（今の本番は条文なしの警告が 2 割弱あった）。条文の正しさは、運営が作る正解ラベルで今後採点する。

## 2. 背景と目的

- 本番の判定モデル `OPENAI_MODEL=gpt-4o-mini` が廃止予定のため、別のモデル・方式へ移行する必要がある。
- 運営の最優先事項は **判定漏れ（警告すべき投稿の見逃し）を出さないこと**。誤検知は管理者が目視で除けるので、一定数減れば良い。
- 移行先の第一候補は、費用が安い Decisions API。廃止の可能性に備え、gpt-6-luna 単体でも判定できること。

## 3. 評価データ

Notion の違反 DB から全レコードを取得し、**管理者の実際の判断を正解**とした。

| 区分 | 件数 | 定義 |
|---|---|---|
| 警告済み（正解 = 違反） | 326 | 管理者が警告を送った（`対応終了`・`期限超過` など、または警告送信日時あり） |
| 対応不要（正解 = 違反ではない） | 1,167 | 管理者が `対応不要` にした |
| 未対応（正解なし） | 240 | 管理者がまだ判断していない。参考として判定だけ付けた |

- 正解付きの 1,493 件を、投稿ごとにランダムに **開発用 568 件・評価用 925 件** に分けた。方針の修正は開発用データの分析だけで行い、成績は評価用データで比べた。
- 注意: 評価用データの取りこぼしを確認したあとで、方針の書き漏らし（宿題の解答の要求・性的な質問など）を 1 回追加している。そのため評価用データの数字はやや甘い。追加前の版でも、評価用データで取りこぼし 7 件・誤検知 106 件と、今の本番を上回っていた。
- データの偏り: 97% が 1 つのワークスペース（海外の受講生が中心）。9 月以降の記録が大半。
- 制約: Notion にあるのは今の本番が通知した投稿だけで、今の本番が見逃した投稿は含まれない。

## 4. 今の本番の問題点

1. **スコアが判定の役に立っていない**: モデルに「違反スコア 0〜100」と「確信度」を文章として出力させているが、警告済みも対応不要もほとんどが「81 点・確信度 0.95」に固まる。警告すべき投稿とそうでない投稿の順位付けの良さ（ROC-AUC）は 0.56 で、ほぼでたらめと同じ。
2. **誤検知が多い**: 通知のうち 78% を管理者が対応不要にしている。主な誤検知は、講座の公式資料（ライブ講義の Zoom・録画・Drive）への案内を「録画共有」、「つながろう」を「出会い目的」と取り違えたもの。
3. **条文が一貫しない**: 内容がほぼ同じ「WhatsApp グループへの招待」に、11-v・11-iv・11-xiii・11-iii（システム妨害）と別々の条文が付いて警告されている。条文なしで送られた警告も 55 件ある。

## 5. 新方式

### 5.1 判定の方針（プロンプト）

問いかけを「規約に違反しているか（点数）」から「運営がこの投稿者に警告を送るべきか（warn / safe）」に変え、管理者の実際の判断から読み取った方針を明記した（`judge_decision.txt`）。

| 判断 | 主な対象 |
|---|---|
| 警告する | 外部のチャットグループ（WhatsApp・Telegram・Discord など）への勧誘や人集め（リンクがなくても）、講座と無関係な宣伝・フォロワー集め・金銭の無心、宗教やネットワークビジネスの勧誘、性的な話題、出会い目的、特定の人物への接触、宿題・試験の解答の要求、嫌がらせ、教材や録画の外部公開 |
| 警告しない | 自己紹介・挨拶・雑談・短い返信（どの言語でも）、個人どうしの連絡先のやりとりだけのもの、講座の公式資料への案内、学習の質問、ルールに関する他の受講生への注意 |

### 5.2 判定の流れ（2 段階）

```
投稿
 ├─ 1段目（経路 A: Decisions API で 1 回の呼び出し）
 │    ├─ 警告すべきか: warn / safe の確率 → P(warn) ≥ 0.5 で違反
 │    └─ 条文: 全条文の確率 → 上位 3 つを候補に
 └─ warn のときだけ 2段目（gpt-6-luna）
      └─ 候補 3 条文から最も違反しているもの 1 つと理由を選ぶ
```

- **確率で判定する**: Decisions API はモデル内部の確率を返すので、文章で書かせた点数と違い、警告すべき投稿とそうでない投稿をよく分けられる（ROC-AUC 0.56 → 0.97）。同じ投稿には毎回同じ答えを返す。
- **条文の選び方**: 方針と条文の対応表（`article_guide.txt`）を使う。外部チャットグループへの勧誘は 11-xiii（無許可の宣伝・勧誘）とした（運営の確認待ち）。
- **予備経路（経路 B）**: Decisions API がエラー・タイムアウト（10 秒）になったら、1 段目を gpt-6-luna の Chat Completions で行う（警告するか・条文の候補 3 つを出す）。2 段目は経路 A と同じ。

### 5.3 切り替え方

環境変数 `DETECTION_MODE`（CDK パラメータ `DetectionMode`）で選ぶ。

| 値 | 動作 |
|---|---|
| `llm_score`（既定） | 今の本番と同じ |
| `decisions` | 経路 A。失敗したら経路 B |
| `luna` | 経路 B だけ（Decisions API が廃止された場合） |

経路 A・B の 2 段目と経路 B の 1 段目は、`OPENAI_MODEL` のモデルを使う。`gpt-6-luna` に設定する。

## 6. 結果

本番コード（`ViolationDetector`）そのものを、実際の API で全 1,733 件に流して計測した。

### 6.1 精度（評価用データ 925 件、うち警告済み 201 件）

| 方式 | 取りこぼし | 誤検知 | 再現率 | 適合率 | F1 | 通知件数 |
|---|---|---|---|---|---|---|
| 今の本番（gpt-4o-mini） | 11 | 665 | 0.945 | 0.222 | 0.360 | 855 |
| 今のプロンプトのまま gpt-6-luna（参考、開発用データ） | 58 / 125 | 35 | 0.536 | 0.657 | 0.590 | — |
| **経路 A（Decisions API）** | **1** | **134** | **0.995** | 0.599 | 0.748 | 334 |
| 経路 B（gpt-6-luna だけ） | 3 | 132 | 0.985 | 0.600 | 0.746 | 330 |

- 正解付き全体（1,493 件）での取りこぼし: 今の本番 21 件、経路 A 2 件、経路 B 4 件。
- 経路 A の取りこぼし 2 件は同じ投稿で、Notion に保存された本文が 500 文字で切れて、勧誘部分が欠けていたもの。本番では全文で判定するので検知できる見込み。
- 未対応 240 件のうち通知の対象になるもの: 今の本番 164 件、経路 A 48 件、経路 B 60 件。

### 6.3 レイテンシ（1 投稿の判定時間、秒）

| 方式 | 平均 | 中央値 | p95 | 警告の投稿 | 警告しない投稿 |
|---|---|---|---|---|---|
| 今の本番 | 1.2 | 1.1 | 1.9 | 1.2 | 1.1 |
| 経路 A | 1.2 | **0.3** | 3.6 | 2.9 | **0.3** |
| 経路 B | 4.6 | 4.2 | 8.2 | 6.0 | 3.9 |

- 経路 A は、大半を占める警告しない投稿が 0.3 秒で終わる。警告の投稿は 2 段目（条文の選択）の分だけ時間がかかる。
- 手元の環境から 8 件同時に流して測った値。Lambda（東京）からの実測とは多少ずれうる。

### 6.4 条文

| | 経路 A | 経路 B |
|---|---|---|
| 警告した投稿に条文が付いた割合 | 100% | 100% |
| 2 段目が候補の 1 位を選んだ割合 | 94% | 97% |
| 経路 A と B の条文の一致（両方が警告した 468 件） | 98% | — |

- 警告済みの投稿では、外部チャットグループへの勧誘が大半のため、ほぼ 11-xiii が選ばれる。宗教の勧誘は 11-v、金銭の無心は 11-x、脅しは community-4、宿題の解答の要求は course-8-iv など、内容に合った条文が選ばれることを実例で確認した。
- 今の本番が記録した条文との一致は 271 件中 49 件にとどまる。ただし、今の本番は同じ行為に別々の条文を付けており、人が条文を選んだ記録もない（警告テンプレートは「標準警告」の 2 種類だけ）。このため一致率は正しさの指標にならない。

## 8. 残っている課題

1. **条文の正解ラベル**: 運営が正解の条文を付ける（警告済み 326 件を本文ごとにまとめた 177 行）。付けたら、記録時・経路 A・経路 B の条文の正解率を採点する。特に、外部チャットグループへの勧誘を 11-xiii と 11-v のどちらにするかを決める。
2. **判定エラー時の扱い**: 経路 A・B の両方が失敗すると、今の本番と同じく「違反なし」となり通知されない。判定漏れを最優先にするなら、「判定できなかった」として通知する変更を検討する。
3. **未見のデータでの確認**: 今回の数字は、方針の修正に評価用データの分析も一部使っているため、やや甘い。今後 Notion に溜まる新しい判断で、同じ評価をもう一度行う。
4. **今の本番が見逃していた投稿**: Notion には今の本番が通知した投稿しかないため、それ以外の投稿での検知力は測れていない。デプロイ後しばらくは、旧方式と新方式の両方で判定して差を記録することを推奨する。
5. **警告時のレイテンシ**: 警告の投稿は約 2.9 秒かかる。問題になる場合は、2 段目を省き Decisions API の条文候補の 1 位を使う（約 0.3 秒、ただし理由の文が付かない）。

## 9. デプロイの手順（運営が実行する）

1. 実装を commit し、PR でレビューする。
2. GitHub Actions の変数 `OPENAI_MODEL` を `gpt-6-luna` にする。
3. `deploy.yml` の `cdk deploy` に `--parameters DetectionMode=decisions` を追加する。
4. Manual Deploy を実行し、`docs/regression_checklist.md` の 1 章（違反検知 → アラート）と 3 章（投稿の編集）を確認する。
5. 問題があれば `DetectionMode=llm_score` で再デプロイすれば元に戻る（gpt-4o-mini が使える間）。
