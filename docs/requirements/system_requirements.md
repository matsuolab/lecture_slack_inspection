## 1. 目的と範囲

### 1.1 目的

松尾研 DX プロジェクトの受講生用の Slack ワークスペース（複数）で、規約に反する投稿を見つけ、運営の管理者に知らせ、管理者の判断で投稿者に警告し、そのあとの対応を Notion で追跡する。

- 最優先は**判定漏れ（警告すべき投稿の見逃し）を出さないこと**。誤検知は管理者が目で見て除ける（移行の報告書 2 章）

### 1.2 範囲

| 範囲に入るもの | 決定 |
|---|---|
| ボットがインストールされたワークスペースの、Bot が参加している**公開チャンネルの投稿すべて**（普通の投稿、スレッドの返信、ファイルを添えた投稿、チャンネルにも送った返信）と、その編集 | D3 |
| 今ある機能 F1〜F12 はすべて続ける | R16 |

範囲に入らないもの（決めたもの）は 7 章。

## 3. 前提と制約

- Slack は投稿・編集のたびにボットへイベントを送り、3 秒以内の返事を求める。返事が無いと同じイベントを送り直す（すぐ・1 分後・5 分後）。60 分間で 95% を超えて失敗すると購読を止められる（1 時間に 1,000 件未満のアプリは対象外）（https://docs.slack.dev/apis/events-api/ 、issues.md ISS-03）
- 判定は OpenAI を使う。本番のモデル gpt-4o-mini は廃止予定で、Decisions API（gpt-6-luna）を主経路とする方式に移行する準備ができている（移行の報告書。デプロイは未）
- 複数のワークスペースで同じ Lambda が動く。ワークスペースごとのトークンと通知先は SSM に置く
- 状態はすべて Notion（違反 DB・条文マスタ・ワークスペース一覧・テンプレート・ヘルスチェック）に置く

## 4. 機能要件

### FR-01 投稿の判定（F1、D3）

- **決定:** 公開チャンネルの投稿すべてを判定する。ファイルを添えた投稿（本文があるもの）とチャンネルにも送った返信を含める
- **現状:** `subtype` の付いた投稿（`file_share`・`thread_broadcast` など）は判定せずに捨てる
- **差:** ISS-08。今の Slack が実際にどの `subtype` を付けるかは要確認（decisions.md の C）
- 受け入れ条件: ファイルを添えた投稿・チャンネルにも送った返信に違反の文を書くと、管理者チャンネルに通知が来る（検証用のワークスペースで確かめる）

### FR-02 判定できなかった投稿（D1・D2・D8）

- **決定（方針）:** 先に第 1 段階（判定できなかったことを必ず記録し、人が判定し直せるようにする。タイムアウトの指定と、送り直しの理由を見る処理を入れる）、そのあと第 2 段階（Slack への返事と判定を分け、自動でやり直し、駄目なものは退避する）
- **決定（失敗の通知）:** 失敗を知らせる仕組み（D8）は一旦なし
- **現状:** OpenAI の障害・タイムアウト・モデルの廃止などで判定の段が失敗すると、黙って「違反なし」になり、記録・通知・エラーのログのどれも残らない。Lambda の 30 秒で打ち切られた場合も同じ。Slack の送り直しは理由を見ずに捨てるので、やり直されない
- **差:** ISS-01（判定の失敗が「違反なし」）、ISS-02（タイムアウトの指定なし）、ISS-03（3 秒の返事）、ISS-32（送り直しを理由を見ずに捨てる）、ISS-15（失敗に気づけない）
- 規模と前提: decisions.md の D1・D2（第 2 段階は、判定の失敗を握りつぶしている作りを変えないと AWS の自動のやり直しが働かない、など）

### FR-03 スタッフの除外（F9、D4）

- **決定:** 今のまま。Slack の名前（`real_name`）に「松尾研」を含む人の投稿は判定しない
- **現状:** 新規の投稿では除外する。編集のイベントでは除外が効かず、スタッフの編集も判定される。名前の取得（`users.info`）が失敗すると、その投稿は判定されない
- **差:** ISS-26（編集で除外が効かない。直すだけの課題＝decisions.md の B）、ISS-09（名前の取得の失敗で判定されない。受講生が名前を変えられるかは要確認）
- 受け入れ条件: 名前に「松尾研」を含む人の新規の投稿と編集は、どちらも判定されない

### FR-04 記録と管理者への通知（F1）

- **決定:** 今の流れを続ける。違反と判定した投稿は、Notion の違反 DB に `未対応` で記録し、管理者チャンネルにボタン付きで通知する
- **現状:** 記録に失敗しても通知は送り、そのボタンには Notion のページが結び付かない。重複の確認（`Message_TS`）が失敗すると「重複なし」として進む。`Message_TS` はチャンネルをまたいで一意でない
- **差:** ISS-12（記録の失敗を無視）、ISS-13（重複の確認）、ISS-23（ボタンの value。今の経路では超えないが、守りは理由の切り詰めだけ）、ISS-11（通知先の無いワークスペースでは、すべての投稿が判定されない）
- 受け入れ条件: 違反の投稿 1 件につき、違反 DB のレコード 1 件と管理者チャンネルの通知 1 件ができ、通知から Notion のレコードが分かる

### FR-05 管理者のボタン（F3、D5-4）

- **決定:** 押せる人は今のまま（管理者チャンネルの参加者の管理で担保する）
- **現状:** 押した時点の状態を確かめないので、2 人がほぼ同時に押すと警告が 2 回送られる。Notion の更新が失敗しても成功として扱い、ボタンを消す。48 時間経過の通知のボタンは、そのあと `対応終了` になっても消えない
- **差:** ISS-14（二重押し・残ったボタン。直すだけ）、ISS-12（更新の失敗を無視）
- 受け入れ条件: 同じボタンを 2 回押しても、警告は 1 回だけ送られる

### FR-06 編集の追跡（F2、D5-3）

- **決定:** 今のまま。警告中の投稿が違反でない内容に編集されたら `対応終了`。違反のままなら管理者チャンネルのスレッドに「編集されました」と返す。`対応終了`・`対応不要` で終わった投稿が編集で再び違反になっても、状態は変えない（スレッドに返すだけ）
- **現状:** 決定と同じ（[現状の仕様](current_system.md) 2.5）
- 注記: D5-3 を「今のまま」にしたので、`対応不要` で終わった投稿をあとで違反の内容に書き換えても、警告の流れには戻らない（ISS-17。運営の判断として記録）

### FR-07 警告から 48 時間たった投稿の通知（F4）

- **決定:** 続ける。警告から 48 時間たっても残っている投稿は `期限超過` にし、管理者チャンネルのスレッドに「再警告」「対応終了」のボタンを出す
- **現状:** 決定と同じ。ただし `team_id` の無いレコードは黙って永久にスキップされる
- **差:** ISS-27（該当の件数は要確認）

### FR-08 再警告のあと（D5-2）

- **決定:** 再警告から一定時間たっても投稿が残っていれば、管理者に知らせる。その先の対応（削除・アカウントの停止など）は運営が人の手で行う
- **現状:** 再警告のあとは期限も通知も無い（新しい機能）

### FR-09 警告した投稿の削除の検出（F5、D6）

- **決定:** 削除の見つけ方は変えない（対応不要。投稿はきちんと削除されるという前提で運用し、今は各人が確かめている）
- **現状:** 5 分ごとに、警告中のレコードを全件読み、1 件ずつ Slack に問い合わせる
- **現状の問題点（記載だけ）:** 次はどれも「削除されていない投稿を、ボットが削除されたと判断して `対応終了` にし、管理者に『削除されました』と知らせる」向きの問題。警告中の違反が追跡から外れる
  - ISS-04: Slack の API のエラー（レート制限・チャンネルから外された等）を「削除された」と扱う（再現済み。`main` にも同じ処理がある）
  - ISS-05: スレッドの返信への警告を「削除された」と誤判定するおそれ（要再現）
  - ISS-06: Slack のレート制限の変更の対象なら、ISS-04 と重なって大量に起きる（要確認）

### FR-10 判定の基準（条文）（F6、D7）

- **決定:** Notion の条文マスタを条文の**正本**にする。ワークスペースごとのローカルルールも続ける
- **現状:** 判定に使うのはリポジトリの `articles.json`（31 条）とローカルルール。条文マスタは表示とローカルルールにだけ使う。リポジトリにあって条文マスタに無い条文が 9 件ある。2026-08-13 のログ（1 日分）では、ローカルルールは一度も使われていなかった
- **差:** ISS-18、ISS-28（ローカルルールの取得がページ送りをしない）

### FR-11 過去の投稿の一括判定（F7、D10）

- **決定:** 役割は今のまま（手動で起動し、過去の投稿を判定して Notion に記録するだけ。管理者チャンネルには知らせない）。判定方式は FR-01 とそろえる
- **現状:** 判定方式の移行の手順では、`app_batch` だけ旧方式（gpt-4o-mini）のまま残る。gpt-4o-mini が廃止されると全件「違反なし」になる。ローカルルールを渡さない、スタッフを除外しない
- **差:** ISS-07、ISS-30（試し実行で投稿の本文をログに出す。NFR-04）
- 受け入れ条件: `app_batch` と `app_inspect` が同じ判定方式・同じモデルで判定する

### FR-12 インストールと許可リスト（F8、D10）

- **決定:** 許可リストが空のときは、今のまま誰でもインストールできる。GAS（Google Apps Script）での許可リストへの登録に使う AWS のアクセスキーは不要
- **現状の問題点（記載だけ）:**
  - ISS-10: 許可リストが空だと、想定外のワークスペースからもインストールでき、その投稿の判定に OpenAI・Notion の費用がかかり、違反 DB に記録が入る
  - ISS-11: インストールの URL に通知先（`channel`）を付けないと、通知先が保存されず、そのワークスペースの投稿がすべて判定されない（直すだけの課題＝B）
  - ISS-20: CDK が GAS 用のアクセスキーを作っているが、使われない（シークレットも取り出せない）。不要と決めたので、作るのをやめるかは実装のときに決める
  - ISS-31: OAuth の `state` が使い捨てになっていない（直すだけ）

### FR-13 ヘルスチェック DB（F10）

- **決定:** 続ける
- **現状:** Lambda ごとに 1 行を上書きするので、エラーの直後に正常な実行があるとエラーが消える。`app_batch`・`app_oauth`・`app_admin` は書かない
- **差:** ISS-15（D8 で失敗の通知を一旦なしにしたので、失敗に気づける手段はこの DB とログだけ）

### FR-14 判定の方式の切り替えとモック（F11・F12）

- **決定:** 続ける（`DETECTION_MODE` の `auto`・`decisions`・`luna`・`llm_score`、検証用の `USE_MOCK_OPENAI`）
- **差:** ISS-19（Decisions API のモデル名を直接書いている、CDK の既定値が gpt-4o-mini、Python の版がそろっていない）

### FR-15 受講生への警告（R7）

- **決定:** 今のまま。元の投稿のスレッドへの公開の返信で警告する（同じチャンネルの人にも見える）。文面は Notion のテンプレート DB

## 5. 機能以外の要件

### NFR-01 判定の品質（R4）

- **決定:** 判定漏れを今の本番以下にする（移行の報告書）。見逃しは、今の評価のデータ（違反 DB にある、管理者の判断が付いた投稿）だけで測る。「違反なし」とした投稿からの抜き取りはしない
- 注記: この測り方では、旧方式も新方式も「違反なし」とした投稿の中の見逃しは、評価のデータに入らないので分からないまま残る（運営の判断として記録）

### NFR-02 応答と時間（R6）

- **現状:** Slack への返事は、判定・記録・通知・ヘルスチェックの書き込みをすべて終えてから返す。コードの上では、違反の投稿は新しい判定方式で OpenAI を 2 回順番に呼ぶ（decisions.md の D2「コードから言えること」）。ログの数値（1 日分・移行前の方式）は運営が別途確かめている
- 3 秒を超えること自体は、今の作りでは実害が無い（送り直しを捨てるため二重の処理は起きず、Lambda は最後まで動く）。害があるのは、最初の 1 回が失敗した投稿を救えないこと（FR-02）

### NFR-03 止まったとき・失敗したとき（R9、D8）

- **決定:** 失敗を知らせる仕組み（アラーム・メール・運営用の Slack）は一旦なし
- **現状:** CloudWatch のアラーム・DLQ が無い。失敗に気づける手段は、ログ（保持 1 週間）とヘルスチェック DB（上書き）だけ（ISS-15）
- 全 Lambda は、Slack の送り直しが重なるのを防ぐため、例外を握りつぶして 200 を返す作り（`docs/regression_checklist.md`）。この作りと FR-02 の第 2 段階は両立しない（D2 の「案 A に要る変更」）

### NFR-04 個人情報（D9、R12）

- **決定:** 受講生の投稿の本文はログに出さない（`app_batch` の試し実行でも、ID と判定の結果だけ）。Notion に残す期間は、運営の個人情報の方針に合わせて後で決める
- **現状:** Notion の違反 DB に、違反と判定した投稿の本文（先頭 500 文字）・投稿者名・判定理由を無期限に残す。`app_batch` の試し実行で、本文の先頭 200 文字を CloudWatch Logs に 1 週間残す（ISS-30）。判定のため、全投稿の本文を OpenAI に送る

### NFR-05 セキュリティと権限（R11）

- **決定:** ボタンを押せる人は管理者チャンネルの参加者で担保する（D5-4）。許可リストが空なら誰でもインストールできるまま（D10）
- **現状の問題点（記載だけ）:** ISS-10（許可リスト）、ISS-14（押した人の権限を確かめない）、ISS-20（使われない長期のアクセスキー）、ISS-31（OAuth の `state`）、ISS-09（名前で見分けるスタッフの除外は、受講生が名前を変えられると偽れる）

### NFR-06 費用（R10）

- **現状:** 新しい判定方式の費用は、今の本番の約 68%（警告の割合を 1% と仮定した平均。移行の報告書）

### NFR-07 運用と保守（R13）

- **現状:** デプロイは GitHub Actions の手動のワークフロー（`deploy.yml`）。手動の回帰確認は `docs/regression_checklist.md`（一部に誤り。照合の記録）。単体テスト 170 件（うち再現テスト 41 件。`tests/repro/` は今の不具合のある動きを固定しているので、直したら期待値を書き換える）
- **現状の問題点:** ISS-16（Notion のレート制限への対策が無い。定期処理は 5 分ごとに全件を読み直す）、ISS-21（`infra/tests` が古い）、ISS-22（作業ツリーに壊れたプロンプトの変更がある）、ISS-25（ドキュメントがコードと食い違っている）

### NFR-09 投稿の増加への備え（D11）

- **現状:** OpenAI のキーと Notion の接続は、それぞれ 1 つを全ワークスペース・全 Lambda で共有する。Lambda の同時実行数に上限は無い。どちらの 429 も扱っておらず、上限にかかると黙って判定漏れ・記録漏れになる
- **現状の問題点:** ISS-33（OpenAI のレート制限。上限は組織・プロジェクトの単位で、キーを増やしても増えない）、ISS-34（Notion の 1 接続 1 分 180 回の上限に、集中した 1 分に約 40 件の投稿で届く＝推計。違反 DB は 25 万行が上限）、ISS-16（Notion の負荷）
- 対処の選択肢とおすすめ: [検討の記録](../research/20261112_scaling_openai_notion.md) の 5・6 章、decisions.md の D11（運営の回答待ち）

### NFR-08 運営が見たい集計（R14）

- **現状:** 集計の機能は無い。運営が Notion の違反 DB を直接見る

## 6. 状態の流れ（`対応ステータス`）

決定を反映した流れ。現状との違いは FR-08（再警告のあとの通知）だけ。

| 今の状態 | きっかけ | 次の状態 | 要件 |
|---|---|---|---|
| （なし） | 違反と判定 | `未対応` | FR-04 |
| `未対応` | 管理者が「警告を送る」 | `警告済み` | FR-05 |
| `未対応` | 管理者が「対応不要」 | `対応不要` | FR-05 |
| `未対応` | 放置 | `未対応` のまま（知らせない） | D5-1 |
| `警告済み` | 48 時間たつ | `期限超過` | FR-07 |
| `期限超過` | 管理者が「再警告」 | `再警告済み` | FR-05 |
| `期限超過` | 管理者が「対応終了」 | `対応終了` | FR-05 |
