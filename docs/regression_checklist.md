# リグレッションテスト チェックリスト（手動 / Slack UI ベース）

Slack 投稿監視 Bot のリグレッションテストです。**デプロイ後にコアロジックが緊急停止していないこと**を、検証用ワークスペースの Slack 上から実際に操作して目視確認します。

## このテストの目的

開発・デプロイによって「黙ってサービスが止まる」事故を防ぐ。

>  **重要な前提**: 本 Bot は全 Lambda が**例外を握りつぶして HTTP 200 を返す**設計です（Slack のリトライ嵐を防ぐため）。
> そのため「Slack がエラーにならない＝正常」ではありません。**期待した副作用（管理者chへのアラート / 投稿者への警告 / Notion レコードの状態）が実際に起きているか**を必ず確認してください。

---

## 事前準備

| 項目 | 内容 |
|---|---|
| 対象環境 | 検証用ワークスペース（本番ではなく staging を推奨） |
| 必要な権限 | 監視対象チャンネルへの投稿権限 / 管理者プライベートチャンネルの閲覧権限 / 対象 Notion DB の閲覧権限 |
| 確認場所① | **監視対象チャンネル**（投稿者への警告スレッドが付く場所） |
| 確認場所② | **管理者プライベートチャンネル**（違反アラートとボタンが出る場所 = `alert_channel_id`） |
| 確認場所③ | **Notion 違反 DB**（`NOTION_DB_ID`、レコードと `対応ステータス`） |
| アカウント | 一般ユーザー役（投稿する人）と 管理者役（ボタンを押す人）の2アカウントがあると確実 |
| デプロイ確認 | テスト開始前に対象 Lambda が最新版にデプロイ済みであること |

### 用語

- **違反投稿**: ガイドライン違反としてスコア 51 以上になる内容の投稿（実環境の判定例を使う。`違反検知` の検証は実際に違反扱いになる文言で行う）
- **セーフ投稿**: 違反スコアが低い、通常の雑談・情報共有
- **管理者ch**: 違反アラートが届くプライベートチャンネル
- **対応ステータス**: Notion 上のライフサイクル（`未対応` → `警告済み` → `期限超過` → `再警告済み` → `対応終了` / `対応不要`）

### 判定の書き方

各ケースで、**結果が期待どおりなら ✅ / 違えば ❌ を記録**し、❌ の場合は「実際に起きたこと」をメモ欄に残してください。

## Slack UI 操作の基本（全章共通）

各章の手順で出てくる基本操作。Slack のデスクトップ版またはブラウザ版を想定します。

### A. チャンネルを開く / 投稿する
1. 左サイドバーの「チャンネル」一覧から対象チャンネルをクリックして開く。一覧に無ければ上部の検索バー（`Ctrl/Cmd + K`）にチャンネル名を入力して移動する。
2. 画面下部のメッセージ入力欄に文章を入力し、`Enter` で送信する。
3. 送信後、自分の投稿がタイムラインに表示されることを確認する。

### B. 投稿を編集する（3章で使用）
1. 編集したい自分の投稿にマウスカーソルを合わせる。
2. 右上に出る「**︙**（その他）」アイコンをクリック →「**メッセージを編集**」を選ぶ。
3. テキストを書き換えて `Enter`（または「保存する」）で確定する。投稿に「（編集済み）」が付く。

### C. アラートのボタンを押す（4章で使用）
1. **管理者プライベートチャンネル**を開く。
2. Bot が投稿した「🚨 違反の可能性を検知」メッセージを探す。
3. メッセージ下部のボタン（承認 / 却下 / 再警告 / 対応終了 など）を**クリック**する。
4. テンプレート選択のプルダウンがある場合は、ボタンを押す前にプルダウンから項目を選ぶ。

### D. 結果の確認場所
- **投稿者への警告**: 元の違反投稿に**スレッド返信**として付く（投稿右の「スレッド」を開いて確認）。
- **管理者chの状態更新**: ボタンを押すと、元のアラートメッセージが「 警告済み」等の**表示に書き換わり、ボタンが消える**。
- **Notion**: ブラウザで違反 DB を開き、対象レコードの `対応ステータス` 列などを確認する。
- **CloudWatch Logs**: AWS コンソール → CloudWatch → ロググループ → 対象 Lambda（`app_inspect` 等）の最新ログストリームを開く。

>  投稿を作るアカウント（一般ユーザー役）とボタンを押すアカウント（管理者役）は分けると、実運用に近い形で確認できます。1人で行う場合は、投稿後にアカウントを切り替えるか、自分の投稿に対して管理者chでボタンを押します。

## 1. 違反検知 → アラート（app_inspect / 最重要コア）

監視対象チャンネルへの新規投稿を受け、違反判定 → Notion 登録 → 管理者chへアラートが出ることを確認する。**ここが止まると Bot の存在意義が失われるため最優先。**

### UI 操作手順（基本フロー 1-1〜1-2）
1. Slack で**監視対象チャンネル**を開く（操作 A-1）。
2. メッセージ入力欄に**違反投稿**の文言を入力し、`Enter` で送信する（操作 A-2）。
3. **管理者プライベートチャンネル**に切り替える。Bot から「 違反の可能性を検知」アラートが届き、ボタンが表示されることを確認する（→ 1-1）。
4. ブラウザで **Notion 違反 DB** を開き、いま投稿した内容のレコードが1件作られ、`対応ステータス` が `未対応` であることを確認する（→ 1-2）。
5. 続けて 1-3〜1-7 の各ケースを、同じ手順（監視対象chに投稿 → 管理者ch / Notion を確認）で実施する。各ケースの「期待結果」と照合する。

| # | 操作（Slack UI） | 期待結果 | 確認場所 | 判定 |
|---|---|---|---|---|
| 1-1 | 監視対象chに **違反投稿** を1件する | 管理者chに「違反の可能性を検知」アラートが届き、**承認 / 却下 等のボタン**が表示される | 管理者ch | ☐ |
| 1-2 | 1-1 の直後、Notion を開く | 同じ投稿の違反レコードが**1件新規作成**され、`対応ステータス` が `未対応`、投稿リンク・条文・確信度が入っている | Notion | ☐ |
| 1-3 | 監視対象chに **セーフ投稿**（普通の雑談）をする | 管理者chに**アラートが出ない**。Notion にも**レコードが作られない** | 管理者ch / Notion | ☐ |
| 1-4 | 1-1 と**全く同じ違反投稿**をもう1件する | アラートは出るが、Notion 側は重複として扱われ**二重レコードが作られない**（Message_TS 重複スキップ） | Notion | ☐ |
| 1-5 | Bot 自身 / 他の Bot による投稿が監視対象chに流れる状況を作る | **無視される**（アラートも Notion 登録もなし） | 管理者ch / Notion | ☐ |
| 1-6 | **表示名に「松尾研」を含むスタッフアカウント**で違反投稿をする | **監視対象外として無視される**（アラートなし） | 管理者ch | ☐ |
| 1-7 | 空メッセージ（テキストなし、ファイルのみ等）を投稿する | エラーにならず**無視される**（アラートなし） | 管理者ch | ☐ |

> **回帰の見抜き方**: 1-1 で「Slack 上は何も起きないが管理者chにアラートが来ない」場合、Lambda は 200 を返しているが内部で失敗している可能性が高い。CloudWatch Logs で `app_inspect` のログ（`action=alert_sent` が出ているか / `error` が出ていないか）を確認する。

## 2. ワークスペース別ローカルルール（app_inspect / 条文フィルタ）

ワークスペース固有の追加条文（Notion 条文マスタの `workspace` 列で紐付いたもの）が判定に反映されることを確認する。

### UI 操作手順
1. 事前に、Notion 条文マスタで**特定ワークスペースにだけ紐づくローカルルール条文**が登録されていることを確認する（`workspace` 列・`有効=True`）。
2. そのワークスペースの Slack に切り替え、監視対象chを開く（操作 A）。
3. **ローカルルールにだけ違反する文言**を投稿する（共通条文には触れない内容）。
4. 管理者chでアラートを確認し、紐づく条文がそのローカルルールであることを Notion で確認する（→ 2-1）。
5. 別のワークスペース（ローカルルール未設定）に切り替え、同じ文言を投稿して挙動の違いを確認する（→ 2-2）。

| # | 操作（Slack UI） | 期待結果 | 確認場所 | 判定 |
|---|---|---|---|---|
| 2-1 | ローカルルールが設定されたワークスペースで、**そのローカルルールにだけ違反する投稿**をする | 違反として検知され、アラートに**そのローカルルールの条文**が紐づく | 管理者ch / Notion | ☐ |
| 2-2 | ローカルルール未設定のワークスペースで同じ投稿をする | ローカルルール条文では違反にならない（共通条文の範囲で判定される） | 管理者ch | ☐ |
| 2-3 | Notion 条文マスタが一時的に取得できない状況でも違反投稿をする | ローカルルール取得に失敗しても**共通条文での判定は継続**し、Bot は停止しない | 管理者ch | ☐ |

## 3. 投稿の編集（app_inspect / violation_transition / 状態機械）

投稿が**編集**されたときの状態遷移を確認する。元レコードの `対応ステータス` によって挙動が変わる4分岐を網羅する。

### UI 操作手順（3-2 を例にした基本パターン）
3-2〜3-3 は「すでに違反レコードがある投稿を編集する」ケースなので、先に違反状態を作ってから編集します。
1. 監視対象chに**違反投稿**をして、管理者chにアラートを出す（1章と同じ）。
2. 管理者chでそのアラートの**承認 / 警告ボタンを押す**（操作 C）。これで Notion の `対応ステータス` が `警告済み` になる（＝アクティブ違反状態を作る）。
3. 監視対象chに戻り、さきほどの**違反投稿を編集**する（操作 B）。
   - **まだ違反のまま**別の文言に編集 → 3-2 を確認（管理者chの**元アラートのスレッド**に「編集された（まだ違反）」返信が付く）。
   - **セーフな内容に編集** → 3-3 を確認（Notion が対応終了になり、スレッドに「対応終了」返信が付く）。
4. 3-1 は逆に、**セーフ投稿を違反内容に編集**して新規アラートが出ることを確認する（事前のレコードは不要）。
5. 編集系の確認は、投稿の「（編集済み）」表示と、管理者chの**スレッド**（メイン投稿ではなく返信）を必ず開いて見る。

| # | 前提（Notion 上の元レコード状態） | 操作（Slack UI） | 期待結果 | 判定 |
|---|---|---|---|---|
| 3-1 | レコードなし（セーフ投稿） | セーフ投稿を**違反内容に編集**する | **新規違反レコードが作成**され、管理者chに新しいアラートが届く（create_new_violation） | ☐ |
| 3-2 | `警告済み`（違反レコードあり） | その違反投稿を**まだ違反のまま別の文言に編集**する | **新規レコードは作られず**、管理者chの**元アラートのスレッドに「投稿が編集されました（まだ違反）」返信**が付く（reply_still_violation） | ☐ |
| 3-3 | `警告済み`（違反レコードあり） | その違反投稿を**セーフな内容に編集**する（違反を解消） | Notion レコードが**対応終了になり**、管理者chの元アラートのスレッドに「対応終了にしました」返信が付く（close_by_edit） | ☐ |
| 3-4 | `未対応`（アクティブでないステータス）でセーフに編集 | 違反解消の編集をする | アクティブ違反ステータス（`警告済み`/`期限超過`/`再警告済み`）でないため、**何も起きない**（no_action） | ☐ |
| 3-5 | 任意 | **本文を変えずに**メタデータだけ変わる編集（リアクション等）を発生させる | **無視される**（本文不変の編集はスキップ） | ☐ |

> アクティブ違反ステータス = `警告済み` / `期限超過` / `再警告済み`。これ以外のときに「違反解消編集」をしても close されないのが正しい挙動。

## 4. 管理者ボタン操作（app_alert / 承認・却下・再警告・対応終了）

管理者chのアラートに付くボタンを押したときの処理を確認する。各ボタンで「投稿者への送信有無」と「Notion ステータス更新値」が変わる。

### UI 操作手順
各ボタンごとに、**新しい違反アラートを1件用意してから**1ボタンずつ検証します（1つのアラートでボタンを押すと表示が更新されてボタンが消えるため）。
1. 監視対象chに**違反投稿**をして、管理者chにアラートを1件出す（1章と同じ）。
2. 管理者chでそのアラートを開く。テンプレート選択プルダウンがある場合は、4-5 では**先にプルダウンから項目を選ぶ**（操作 C-4）。
3. 検証したいボタン（承認 / 却下 / 再警告 / 対応終了）を**1つだけクリック**する。
4. 3つの場所を確認する:
   - **元の違反投稿のスレッド**を開き、警告/再警告メッセージが届いたか（承認・再警告のみ）。
   - **管理者chのアラート表示**が「 警告済み」等に更新され、ボタンが消えたか（操作 D）。
   - **Notion** の `対応ステータス` が期待値（警告済み / 対応不要 / 対応終了 等）に変わったか。
5. 次のボタンを検証するときは、**新しい違反投稿でアラートを作り直してから**行う。
6. 4-6 は、4で表示が更新されたアラートのボタンが**消えていて再度押せない**ことを目視確認する。

| # | 押すボタン | 期待結果（投稿者側） | 期待結果（Notion） | 期待結果（管理者ch） | 判定 |
|---|---|---|---|---|---|
| 4-1 | **承認 / 警告**（approve） | 元の**違反投稿のスレッドに警告メッセージ**が届く | `対応ステータス` が **`警告済み`** になり、警告日時・対応者が記録される | 元アラートが**「 警告済み」表示に更新**され、ボタンが消える | ☐ |
| 4-2 | **却下 / 対応不要**（dismiss） | 投稿者への**警告は送られない** | `対応ステータス` が **`対応不要`** になる | 元アラートが**「 対応不要」表示に更新**される | ☐ |
| 4-3 | **再警告**（rewarn） | 元の違反投稿のスレッドに**再警告メッセージ**が届く | 再警告日時・対応者・`再警告済み` 相当の情報が記録される | 元アラートが**「再警告済み」表示に更新**される | ☐ |
| 4-4 | **対応終了**（close） | 投稿者への送信は**なし** | `対応ステータス` が **`対応終了`** になる | 元アラートが**「 対応終了」表示に更新**される | ☐ |
| 4-5 | テンプレート選択プルダウンがある場合、テンプレを**選んでから**承認/再警告を押す | 選んだテンプレ文面で警告が届く | 選択したテンプレート（Notion リレーション）が紐づく | — | ☐ |
| 4-6 | 同じアラートのボタンを**もう一度押せるか**確認（更新後はボタンが消えているはず） | 二重送信が起きない（ボタンが消えているため押せない） | ステータスが二重更新されない | — | ☐ |

> **回帰の見抜き方**: ボタンを押したのに「投稿者に警告が来ない」「Notion のステータスが変わらない」「管理者chの表示が更新されない」のいずれかが起きたら回帰。CloudWatch Logs で `app_alert` の `action=exec_<action_id>` と後続のエラーを確認する。origin 情報（投稿元ch/ts）が欠けているとボタン処理が失敗するので、4-1/4-3 が失敗する場合はアラート生成側（app_inspect）の value 埋め込みを疑う。

## 5. リマインド（app_remind / スケジュール起動）

未対応のまま一定時間経過した違反のリマインドと、削除済み投稿の検知を確認する。スケジュール起動のため、テスト時は手動でトリガーする。

### 操作手順（スケジュール Lambda のため UI 投稿ではなく手動起動）
1. リマインド対象を用意する。すぐに用意できない場合は、Notion で既存の `未対応` 違反レコードの登録日時を**しきい値より前**に書き換えて、対象に仕立てる。
2. AWS コンソール → Lambda → `app_remind` の関数を開き、「**テスト**」タブから空イベント `{}` で実行する（または CloudShell で下記コマンド）。
3. 実行後、**管理者ch**にリマインド通知が届いたか、Notion のステータスが更新されたかを確認する。
4. 削除検知（5-3）は、元の Slack 投稿を削除してから 5-1 と同じ手順で実行し、Notion 側の処理を確認する。

| # | 操作 | 期待結果 | 確認場所 | 判定 |
|---|---|---|---|---|
| 5-1 | リマインド対象（経過時間しきい値を超えた `未対応` 違反）を用意し、`app_remind` を手動実行する | 対象違反について**管理者ch にリマインド通知**が届く | 管理者ch / Notion | ☐ |
| 5-2 | しきい値未満の新しい違反しかない状態で実行する | リマインドが**飛ばない**（誤通知しない） | 管理者ch | ☐ |
| 5-3 | 元の違反投稿が**削除されている**レコードがある状態で実行する | 削除検知が働き、レコードが適切に処理される（仕様に沿った状態に更新される） | Notion | ☐ |
| 5-4 | リマインド実行が**最後まで完走**する | ログにエラーが出ず正常終了（`action=completed`）。途中の1件で失敗しても全体が止まらない | CloudWatch Logs | ☐ |

> 手動実行手順例（CloudShell 等）: `aws lambda invoke --function-name <app_remind の関数名> /dev/stdout`

## 6. 過去メッセージ一括スキャン（app_batch / 手動起動）

チャンネルの過去メッセージを遡って一括検査する。`aws lambda invoke` で起動する。

### 操作手順
1. 対象の `team_id` と `channel_id` を控える（Slack でチャンネルを開き、URL 末尾の `Cxxxx` がチャンネルID。ワークスペースの `Txxxx` がチームID）。
2. AWS コンソール → Lambda → `app_batch` の「**テスト**」タブ、または CloudShell で下記ペイロードを使って起動する。
3. **まず `dry_run: true`** で実行し（6-1）、ログに違反候補だけが出て Notion に登録されないことを確認する。
4. 問題なければ `dry_run` を外して本実行し（6-2）、戻り値の件数と Notion 登録を確認する。

| # | 操作 | 期待結果 | 判定 |
|---|---|---|---|
| 6-1 | `team_id` と `channel_id` を指定し、**`dry_run: true`** で実行する | 違反候補がログに出るだけで、**Notion には登録されない**（安全確認用） | ☐ |
| 6-2 | `dry_run` なしで実行する | 過去の違反投稿が Notion に登録され、戻り値に `scanned` / `violations` / `duplicates` 件数が返る | ☐ |
| 6-3 | 既に登録済みの違反を含む範囲を再スキャンする | **重複は登録されず** `duplicates` にカウントされる | ☐ |
| 6-4 | `team_id` または `channel_id` を**指定せずに**実行する | エラー応答が返る（`team_id and channel_id are required`）が、Lambda 自体はクラッシュしない | ☐ |
| 6-5 | 1回の実行上限件数を超えるチャンネルでスキャンする | 上限で打ち切られ、`next_oldest` で続きが分かる（取りこぼし・暴走しない） | ☐ |

実行ペイロード例:
```json

```

## 8. 入口のガード / 耐障害性（緊急停止しないことの保証）

「壊れても**サービス全体は止まらず**、不正リクエストは弾く」ことを確認する。**ここが本チェックリストの本質**。

### 操作手順（多くは Slack の通常 UI では再現できないため、間接的に確認する）
- **8-1 署名検証**: Slack の正規リクエストは常に署名が正しいため、UI から不正署名は作れない。Slack App 設定の **Signing Secret を変更**してデプロイ環境と不一致にし、その状態で違反投稿をしてもアラートが出ない（拒否される）ことで確認する。確認後は必ず元に戻す。CloudWatch で `verify_signature result=fail` を確認するのが確実。
- **8-2 リトライ**: 通常 UI では起こせない。Slack 側のタイムアウトを誘発するのは難しいため、**CloudWatch Logs で過去に `retry_skip` ログが出ている**こと、または同一イベントで二重アラートが出ていないことをもって正常とみなす。
- **8-3 URL 検証**: Slack App 設定の「Event Subscriptions」で **Request URL を再保存**すると `url_verification` チャレンジが飛ぶ。URL 欄に緑の「Verified ✓」が出れば成功。
- **8-4 外部障害**: 最も重要。再現するには、検証環境で **Notion の API キーを一時的に無効な値に差し替える**等で外部呼び出しを失敗させ、その状態で違反投稿をする。**Slack 側でエラーやリトライ嵐が起きず**、CloudWatch にだけエラーが残ることを確認する。確認後はキーを必ず元に戻す。
- **8-5 team_id 欠落**: 通常 UI では起きない。CloudWatch で該当ログが出た際にハンドラがクラッシュしていないことで確認する（積極再現は不要）。

>  8-1 / 8-4 は設定やキーを一時的に壊す操作です。**検証用環境でのみ**実施し、確認後は必ず元の値に戻してください。本番環境では実施しないこと。

| # | 状況 | 期待結果 | 判定 |
|---|---|---|---|
| 8-1 | Slack 署名が不正なリクエストが来る（通常運用では起きないが、改ざん/誤設定時） | `401`（または不正として拒否）。処理は実行されない | ☐ |
| 8-2 | Slack が同じイベントを**リトライ**送信する（`x-slack-retry-num` 付き） | リトライは**スキップ**され、二重にアラートが飛ばない | ☐ |
| 8-3 | Slack の URL 検証（`url_verification`）チャレンジが届く | challenge をそのまま返す（Events API 設定が通る） | ☐ |
| 8-4 | Notion / OpenAI / Slack のいずれかが一時的に応答しない状態で違反投稿が来る | Bot は `200` を返し、**Slack 側でリトライ嵐やエラー表示にならない**（CloudWatch にエラーは残るが、ユーザー体験は止まらない） | ☐ |
| 8-5 | `team_id` を特定できないイベントが来る | 適切にエラー応答し、ハンドラがクラッシュしない | ☐ |

>  8-4 が本 Bot の設計上もっとも重要。外部サービス障害時でも Slack のリトライ嵐を起こさず、復旧後に手動でフォローできる状態であること。
