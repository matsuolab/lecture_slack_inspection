# 機能要件の明確化

機能依頼は、依頼者の頭の中にある完成イメージの一部しか言葉になっていないことが多い。推測で作ると「思っていたのと違う」で手戻りが大きくなるので、実装前に **何を作り・何を作らず・どうなれば完成か** を短時間で合意する。

このボットは複数の受講生ワークスペースで本番稼働していて、変更は受講生への警告や管理者への通知としてそのまま表に出る。誤検知・通知漏れ・二重通知の影響が大きいので、振る舞いの合意を特に丁寧にする。

ただし質問攻めは依頼者の負担になる。コードを読めば分かることは自分で調べ、**答えによって実装が変わる、ユーザーにしか決められないこと** だけを聞く。

## 1. 先に調べる（質問する前に）

- 依頼に関係するコード、既存の類似機能、データ構造、テストを読む
- プロジェクトの CLAUDE.md と `.claude/rules/`、`docs/` の設計資料を確認する
  - 全体の構成: `docs/system_architect.md`、`docs/aws_architecture.md`
  - Notion の DB とプロパティ: `docs/notion_db_schema.md`
  - Slack の入力: `docs/lambdaA_input_event.md`（イベント）、`docs/lambdaB_input_interactivity.md`（ボタン操作）、`docs/alert_blockkit.md`（通知の見た目）
  - 手動の回帰確認: `docs/regression_checklist.md`
- 違反検知に関わるなら `lambda/app_inspect/services/violation_detector.py` のモジュール docstring を読む（RAG と NG ワードの高速判定は削除済み）
- 調べた結果から「たぶんこうするのが妥当」というデフォルト案を自分で持つ。質問はその案を確認・選択してもらう形にする
- 仕様書に「今のコードはこう動く」と書くときは、`.claude/rules/evidence.md` に従って根拠を残す（行番号と基準のコミット、再現したなら `tests/repro/` のテスト、外部の仕様なら公式の URL）。根拠を残せない記述は「要確認」と書く
- 既存の課題の一覧（`docs/requirements/issues.md`）と要件定義（`docs/requirements/`）を読み、関係する課題・要件の ID を仕様書に書く。不具合を直すだけで、もともとの要件（`docs/requirements/decisions.md` の R 章）を落としていないかを確かめる

## 2. 曖昧な点を洗い出す

次の観点を見渡し、曖昧で、かつ答え次第で実装が変わるものだけを拾う。全部を聞く必要はない。

| 観点 | 確認すること |
|---|---|
| 目的・利用者 | 誰が何のために使うか（受講生 / 運営の管理者 / 松尾研スタッフ） |
| スコープ | 今回どこまでやるか、やらないことは何か |
| 対象ワークスペース | 全ワークスペース共通か、特定のワークスペースだけか（ローカルルール・設定の持ち方が変わる） |
| 振る舞い | 入力（Slack のイベント・ボタン・スケジュール）→ 出力（返信・管理者 ch への通知・Notion の更新）、文言、デフォルト値 |
| 受講生への見え方 | 受講生に何が見えるか（警告の文言・公開スレッドか DM か）、誤検知したときの影響 |
| 検知 | 判定プロンプト・条文・閾値（`violation_score >= 51`）を変えるか、既存の判定への影響、評価方法（`evals/` の promptfoo） |
| データ | Notion の DB・プロパティの追加や変更（`docs/notion_db_schema.md`）、`対応ステータス` のライフサイクル、既存レコードの扱い |
| Slack の権限 | 新しい API に OAuth スコープの追加が要るか（要るなら各ワークスペースで再インストールが必要） |
| エッジケース・エラー | 編集・削除・スレッド返信・Bot の投稿、Slack のリトライ、Notion / OpenAI / Slack の API の失敗 |
| 既存への影響 | 他の Lambda、編集イベントの状態遷移（`violation_transition.py`）、インフラ（`infra/stacks/infra_stack.py`）、SSM の設定 |
| 非機能 | OpenAI のコスト（投稿数 × トークン）、Lambda のタイムアウト、Slack の 3 秒ルール |
| 完成条件 | どうなれば完了か、どう確認するか（pytest と、デプロイ後の手動確認） |
| 実装方針 | 妥当な設計が複数あるときのトレードオフ |

## 3. 質問する

- AskUserQuestion を使う。1 回につき最大 4 問、各問に具体的な選択肢を 2〜4 個。推奨案を先頭に置いて「(Recommended)」を付け、description にトレードオフを書く
- 自由回答でしか答えられない聞き方は避け、調べた結果に基づく案を出す

  - 悪い例: 「通知はどうしますか？」
  - 良い例: 「違反を取り消したとき受講生に知らせる？」→ `元の警告スレッドに返信 (Recommended)`: 既存の Slack 返信の仕組みを使えて、受講生が経緯を追える / `通知しない`: 実装は軽いが受講生は取り消しに気づかない / `DM で知らせる`: 本人にだけ届くが、`im:write` などのスコープが今の設定（CDK の `SlackBotScopes`）に無ければ、追加と全ワークスペースの再インストールが要る

- 原則 1 ラウンド、多くても 2 ラウンドで終える。残った細部は合理的なデフォルトを選び、仕様書の「前提・仮定」に書いておく（ユーザーが後から直せるように）
- 依頼がすでに十分明確なら質問は省き、仕様書の作成と承認だけ行う

## 4. 仕様書を書く

**保存先**
- `docs/specs/YYYYMMDD_<feature-slug>.md`（このリポジトリのルート `lecture_slack_inspection/` から見たパス）
- 日付は今日、slug は英小文字とハイフン（例: `20261013_dismiss-notice.md`）

**テンプレート**（該当しない節は「なし」と書くか削ってよい）

```markdown
# <機能名>

- 作成日: YYYY-MM-DD
- ステータス: Draft
- 依頼: > ユーザーの依頼文（原文のまま）

## 背景・目的
なぜ必要か、誰が使うか（1〜3 文）

## スコープ
### やること
-
### やらないこと
-

## 振る舞い
入力（Slack のイベント・ボタン・スケジュール）→ 処理 → 出力（Slack への返信・管理者 ch への通知・Notion の更新）。
受講生と管理者のそれぞれに何が見えるか。

## 技術方針
- 変更・追加するファイル / モジュール（どの Lambda か）
- Notion の DB・Slack のスコープ・SSM・CDK（環境変数・IAM・スケジュール）の変更
- 採用しなかった案と理由（あれば）

## エッジケース・エラー処理
-

## 受け入れ基準
- [ ] 具体的で確認可能な条件（テスト or 手動確認手順）

## デプロイ後の手動確認
`docs/regression_checklist.md` の該当する章（「変更範囲ごとの最低限テスト」を参照）と、この機能で追加する確認手順。

## 決定事項ログ
| 質問 | 回答 | 決めた人 |
|---|---|---|
|  |  | ユーザー / Claude（デフォルト採用） |

## 前提・仮定 / 未決事項
-
```

受け入れ基準は「〜が動く」のような曖昧な書き方ではなく、「`tests/unit/test_app_alert.py` が通る」（実行方法は `.claude/rules/gemini-delegation.md`）「`対応ステータス` が `未対応` のレコードで却下ボタンを押すと `対応不要` になり、管理者 ch のメッセージからボタンが消える」のように、第三者が確認できる形で書く。完了判定の拠り所になるため。

## 5. 承認を得る

- 仕様書のパスと要点（やること / やらないこと / 受け入れ基準）をチャットで短く示し、AskUserQuestion で「この仕様で実装する / 修正したい」を確認する
- 修正があれば仕様書を更新して再確認する
- 承認されたらステータスを `Approved` にして実装に入る

## 6. 実装と完了報告

- 実装は `.claude/rules/gemini-delegation.md` に従い、仕様書をもとに指示書を書いて Gemini に依頼し、Claude がテストとレビューをする
- 実装中に仕様にない判断が必要になったら、小さなものは決めて決定事項ログに追記し、大きなもの（スコープ・データ構造・受講生への見え方・外部への影響が変わる）は手を止めて聞く
- 完了時に受け入れ基準を 1 つずつ確認してチェックを付け、ステータスを `Implemented` にする。満たせなかった基準があれば正直にそう報告する。デプロイ後の手動確認はユーザーが行うので、確認する章と手順を報告に含める
- **push・デプロイ・PR マージは行わない。** このプロジェクトのデプロイは `cdk deploy` と GitHub Actions の Manual Deploy（`deploy.yml`）で、全ワークスペースの本番にすぐ反映される。main はチームの共有ブランチなので直接 push しない。作業はローカルでの確認までとし、push・PR・デプロイはユーザーに委ねる（フックでもブロックされている）。commit は main 以外の作業ブランチなら区切りごとに行ってよい（main では行わない。`.claude/rules/memo-branch.md`）
