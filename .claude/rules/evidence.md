# 根拠の残し方（「再現済み」「確認済み」と書くとき）

課題の一覧（`docs/requirements/issues.md`）、現状の仕様、調査の記録、仕様書、レビューの結果などで、
**根拠があるとする記述（確度を「再現済み」「確認済み」とする、「コードはこう動く」と言い切る、数値を挙げる）には、必ず第三者が後からたどれる根拠を git の管理下に残す。**
根拠を残せないなら、確度を下げて書く（「要再現」「要確認」）。

## なぜ

2026-11-11〜12 の要件定義の作業で、課題の再現スクリプト（40 項目）とログの集計を scratchpad に置いたため、セッションの切り替わりで消えた。
「再現済み」と書いた課題を、誰も確かめ直せなくなった。`.claude/` 配下（`.claude/pending/` を含む）も git の管理外なので、根拠の置き場所にならない。

## 確度ごとに残すもの

| 確度 | 残すもの | 置き場所 |
|---|---|---|
| 再現済み | 本物の関数をモックで呼び、現象を確かめるテスト。**今の（不具合のある）動きをそのまま assert する**（直したらテストが失敗し、直した人が期待値を書き換える） | `tests/repro/test_iss<番号>_<内容>.py`。文書には pytest のノード ID（`tests/repro/test_iss04_....py::test_...`）を書く |
| 確認済み（コード） | `パス:行` と、その行番号を数えた**基準のコミット** | 文書の中。行番号は `git show <基準>:<パス> \| sed -n '<行>p'` で 1 ファイルずつ確かめる。作業ツリーが基準と違うファイルでは、作業ツリーで数えない |
| 確認済み（外部の仕様） | 公式の資料の URL と、確かめた日付、書いてある内容の要旨 | 文書の中 |
| 数値（ログ・データの集計） | 集計のスクリプト（データは含めない）、入力（どのファイル・期間・条件）、件数（標本の大きさ）、そのときのコードの版 | スクリプトは `docs/requirements/evidence/` など git の管理下。データ（受講生の投稿・ログ）は commit しない（`.gitignore` 済み）。文書には集計値だけを書く |

- 再現のテストは、書いた時点で Claude が実行して通ることを確かめる。通らなかったら「再現済み」と書かない
- 再現のテストもコードなので、作成は `.claude/rules/gemini-delegation.md` に従って Gemini に依頼する。テストが本当にその現象を確かめているか（モックが現象を作ってしまっていないか）は Claude がレビューする
- 根拠が消えた・古くなった（コードが変わった）ことに気づいたら、確度を下げるか、根拠を作り直す
- 小さい標本（例: 1 日分のログ）から出した結論は、標本の大きさと期間を結論の横に書く。別の版のコード（移行前の判定方式など）のログから今の版の結論を出さない
- 作業の成果（文書・テスト・集計のスクリプト）は、未コミットのまま長く置かない。main 以外の作業ブランチなら区切りごとに commit する。次の Claude のための作業記録（引継ぎ書など）は、根拠とは分けて `claude/memo` に置く（`.claude/rules/memo-branch.md`）

## 置いてはいけない場所

- scratchpad（`/tmp/claude-*`）: セッションが変わると消える
- `.claude/pending/`・`.claude/gemini_logs/` など: git の管理外（`.claude/` のうち作業ブランチで管理しているのは `rules/` と `skills/` だけ）
- 受講生のデータ（`output.json`・`violation_data.json`・`team_logs.json`・`output.csv`）と同じ場所への書き出し
